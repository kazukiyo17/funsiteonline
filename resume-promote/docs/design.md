核心目标：部署一个在线简历优化工具——**自建前端页面**托管于 EdgeOne Pages（或其它静态托管），用户在公网页面上传/填写个人简历（文件/文字）和目标岗位JD（文件/文字）；**由自有后端**调用 Dify 工作流完成 AI 优化，前端将优化后的文本与 **HTML 简历**在页面内展示（如可复制文本 + iframe 安全预览），全程**不采用**「Dify EdgeOne Pages 插件自动部署站点」的方式。
核心适配点：1.  EdgeOne Pages：承载静态资源（HTML/CSS/JS），依托全球加速与简化发布，页面加载流畅；2.  用户操作：简历/JD 双通道（文件+文字），交互简单；3.  功能闭环：后端编排 Dify Workflow，前端展示优化结果与 HTML，无需用户单独下载简历文件即可预览；4.  稳定展示：工作流侧生成完整、无外链依赖的 HTML，前端侧采用隔离预览与安全策略（详见 [frontend-architecture.md](./frontend-architecture.md)），降低解析异常与安全风险。
一、前期准备（必做，确保部署顺利）
1.  账号与工具准备
- 核心账号：Dify账号（https://dify.ai）—— 搭建 AI 简历优化工作流；EdgeOne账号（https://edgeone.cloud.tencent.com）—— 托管**自建前端**静态资源并生成公网访问链接。
- 后端运行环境：用于部署「调用 Dify Workflow」的 HTTPS API（如云函数 SCF、轻量服务器、容器服务或厂商提供的边缘函数等），与 EdgeOne Pages **可为不同云资源**，只需浏览器能访问该 API（配置 `API_BASE` / CORS 或同源代理）。
- 辅助工具：①  文件格式转换工具（如SmallPDF）—— 确保用户上传的简历/JD为Word/PDF格式（适配Dify文件上传）；②  在线HTML预览工具（如HTML Preview）—— 测试AI生成的HTML简历是否正常渲染；③  文本编辑器（如记事本、VS Code）—— 临时保存HTML代码（备用）。
2.  素材准备（用于测试，避免部署后功能异常）
提前准备1份示例简历（Word/PDF+纯文本两种格式）、2份不同岗位JD（如运营岗、行政岗，同样准备文件+纯文本格式），用于部署后测试上传、优化、HTML展示全流程，确保无报错。
3.  模型选择（确保AI优化精准、HTML生成规范）
登录Dify后，选择支持长文本解析、逻辑分析的大模型（推荐GPT-4o、Claude 3.5），免费额度完全满足个人部署和测试需求，无需额外付费，且能确保HTML代码生成无语法错误。
二、Dify工作流搭建（零代码配置工作流，核心步骤，决定功能落地）
核心逻辑：用户在**自建站点页**上传/输入简历+JD → **后端**将输入传给 Dify Workflow → Dify 内各节点完成解析、优化、生成 HTML 与建议 → 后端将结构化结果返回浏览器 → 前端展示文本并在隔离环境中预览 HTML。（工作流在 Dify 内自动化执行；站点与 API 由你方部署，见第三节。）
步骤1：创建Dify应用
1. 登录Dify，点击「Create App」，选择「Workflow（工作流）」，应用名称可设为「简历优化工具」等。
2. 选择已准备好的模型（如GPT-4o），保存后进入工作流编辑界面，开始搭建6个核心节点（确保每个节点关联正确，避免联调时断层）。
步骤2：搭建6个核心节点（逐一配置，直接复制提示词即可）
节点1：用户输入节点（核心：支持简历/JD上传+文字输入）
作用：接收用户上传的简历、JD文件，或用户直接输入的文本内容，为后续AI优化提供数据源，配置如下（均为选填，用户可任选一种方式提交，降低操作门槛）：
- 字段1：「个人简历（文件）」，类型「文件上传」，支持格式「Word/PDF」，提示语：「请上传你的个人简历（Word/PDF格式），无需手动输入」；
- 字段2：「个人简历（文字）」，类型「长文本」，提示语：「若未上传简历文件，可直接粘贴简历文字内容」；
- 字段3：「岗位JD（文件）」，类型「文件上传」，支持格式「Word/PDF」，提示语：「请上传目标岗位JD（Word/PDF格式），无需手动输入」；
- 字段4：「岗位JD（文字）」，类型「长文本」，提示语：「若未上传JD文件，可直接粘贴JD全文」；
- 补充提示：「请至少提交1种简历和1种JD，提交后系统将自动优化并生成HTML简历，直接在页面展示」。
关键说明：适配Dify文件上传限制，若用户上传文件提示异常，可引导其使用文本输入方式，或提前将文件转换为支持格式，避免因文件问题影响部署后使用。
节点2：LLM节点（解析JD+分析简历差距）
作用：自动解析用户上传/输入的JD和简历，提取JD核心要求，分析简历与JD的差距，为后续优化提供依据，提示词直接复制粘贴（无需拆分system和user，Dify自动适配）：
你是资深HR+简历优化专家，负责解析JD（文件/文字）和个人简历（文件/文字），完成以下2件事：
1.  提取JD核心信息：优先识别JD文件中的内容，若未上传文件则识别JD文字内容，精准提取目标岗位的核心技能、工作要求、任职资格、重点工作内容，用简洁的语言汇总（分点，不冗余）；
2.  分析简历与JD的差距：优先识别简历文件中的内容，若未上传文件则识别简历文字内容，对比JD核心要求，找出简历中缺失的JD关键词、未突出的匹配点、需要优化的内容（如工作经历表述、技能缺失），标注差距重点。
输出格式：先输出JD核心提取，再输出简历差距分析，语言简洁，重点突出，不添加多余内容。

节点3：LLM节点（全自动优化简历）
作用：基于节点2的分析，优化简历内容，突出与JD匹配的亮点，量化工作成果，为生成HTML简历提供规范的纯文本基础，提示词直接复制：
你是专业简历优化师，根据以下JD核心要求、简历差距分析，优化用户简历（优先识别简历文件内容，未上传文件则识别简历文字内容），要求如下：
1.  内容贴合：将JD核心关键词自然融入简历，突出与岗位匹配的工作经历、技能、成果，删除与岗位无关的内容；
2.  成果量化：优化工作经历表述，用数据量化成果（如“负责活动运营”改为“负责活动运营，吸引500+用户参与，转化率提升20%”）；
3.  结构清晰：简历结构按照“个人信息→核心技能→工作经历→教育背景→项目经历”排列，重点内容（与JD匹配部分）优先展示；
4.  格式规范：优化后的简历可直接复制使用，段落清晰，无冗余，关键词用【】标注（便于HR捕捉，后续HTML将高亮该部分）；
5.  贴合用户基础：不虚构经历，基于用户原有简历（文件/文字）优化，补充合理的表述，不夸大事实。
输出：仅输出优化后的完整简历（纯文本，无需格式，用于后续生成HTML文件），无其他解释、无多余内容。

节点4：LLM节点（生成可嵌入网页预览的HTML简历）
作用：基于优化后的纯文本简历，生成标准 HTML，便于在**自建前端**中用 iframe（如 `srcdoc`）等方式嵌入预览，避免外链依赖导致的加载失败，提示词侧重「独立完整文档 + 内联样式」：
你是专业前端开发+简历优化专家，根据优化后的纯文本简历，生成可在浏览器中直接渲染的完整 HTML 简历文件，要求如下：
1.  格式标准：生成完整的HTML文件（包含<!DOCTYPE html>、<html>、<head>、<body>标签），代码规范，无语法错误，可被前端作为字符串嵌入 iframe 预览，无需额外打包；
2.  样式适配：添加基础简洁的CSS样式（内嵌在<style>标签中，不依赖外部资源），适配网页展示，字体用微软雅黑/宋体（清晰易读），排版整齐，间距合理，原文本中【】标注的JD关键词用橙色高亮，整体风格专业简洁，符合职场规范；
3.  内容一致：HTML简历内容与优化后的纯文本简历完全一致，结构保持“个人信息→核心技能→工作经历→教育背景→项目经历”，不添加额外内容、不遗漏任何信息；
4.  嵌入适配：无需依赖外部图片、外链 CSS/JS，确保在静态站点中以 iframe 等方式展示时即可正常渲染，降低「资源不可用或不支持的网页类型」类问题；
5.  输出规范：仅输出完整的HTML代码，不添加任何解释、注释，便于后端原样返回给前端展示。
优化后的纯文本简历：#[节点3输出]#
节点5：LLM节点（生成个性化提升建议）
作用：针对简历差距，给出可落地的提升建议，辅助用户进一步完善简历，提示词直接复制：
你是职场提升顾问，根据简历与JD的差距，给出个性化、可落地的提升建议，重点满足以下要求：
1.  紧急项目建议：推荐1-2个「1-3天可完成」的小项目，贴合目标岗位需求，无需复杂技术，能快速补充简历亮点，详细说明项目做法、可呈现的成果；
2.  技能补充建议：针对缺失的核心技能，给出1-2个快速学习方法（如1天速成的在线课程、免费学习资源）；
3.  简历细节建议：补充简历排版、表述细节等优化点，同时可补充HTML简历的简单调整建议（如颜色、字体微调），让简历更专业；

输出格式：分「紧急项目建议」「技能补充建议」「简历细节建议」3部分，每部分简洁明了，可直接落地。

### 四、使用提示
1.  HTML 简历为完整文档字符串，自建前端应在隔离环境（如 sandboxed iframe）中预览，具体见 [frontend-architecture.md](./frontend-architecture.md)；
2.  若预览异常，先检查 HTML 是否完整、是否含违规外链脚本；
3.  可复制 HTML 保存为 .html 本地查看。
步骤3：测试Dify工作流（关键，避免部署后功能异常）
1. 点击工作流右上角「测试」，分别测试两种输入方式：① 上传简历文件+JD文件；② 粘贴简历文字+JD文字，提交后查看输出结果。
2. 重点检查：HTML代码是否完整、复制后在文本编辑器中打开是否正常渲染、关键词是否高亮、无语法错误。
3. 若输出异常（如HTML代码缺失、优化内容不贴合JD），微调对应节点的提示词（无需大幅修改），重新测试，直至所有输出正常。
4. 测试通过后，点击「Publish」发布 Dify 应用；在 **Settings → API Access** 创建 **API Key**，仅用于后端环境变量（**勿写入前端或静态仓库**）。记录工作流对应的 API 调用方式、输入变量名与输出字段，供后端映射。
三、自建站点与 EdgeOne Pages 部署（非插件自动部署）
本节描述「静态前端 + 后端调 Dify」的上线方式：**不使用** Dify Marketplace 中的 EdgeOne Pages 插件把工作流输出自动推送到站点。

整体链路：`用户浏览器` → `EdgeOne Pages 上的静态页面` → `HTTPS 请求自有 /api` → `后端（含 DIFY_API_KEY）` → `Dify Workflow API` → 返回结构化数据 → 前端渲染与 HTML 预览。

步骤1：对接 Dify API（后端）
1. 推荐使用本仓库 **Pages Cloud Functions**：`cloud-functions/api/optimize.js` → **`POST /api/optimize`**。环境变量、与工作流变量名的映射、为何不用 Edge Functions，见 [CONFIGURATION.md](./CONFIGURATION.md)。根目录 **`edgeone.json`** 已将 **`maxDuration`** 设为 **120** 秒以适配长工作流。
2. 亦可自建其它运行时：在服务端配置 `DIFY_API_KEY`、（自建实例时）`DIFY_API_URL` 等，参见 [frontend-architecture.md](./frontend-architecture.md) 第七节；契约与第八节一致。
3. 跨域：与静态页同源时可不调 CORS；本地或跨域时需配置 `CORS_ORIGIN`（函数内已处理 `OPTIONS`）或网关反代。

步骤2：构建前端并部署到 EdgeOne Pages
1. 按 [frontend-architecture.md](./frontend-architecture.md) 组织 `index.html`、`css/`、`js/`。与 Cloud Functions **同属一个 Pages 项目**时，`API_BASE` 保持 **空字符串** 即可（请求 `/api/optimize`）。
2. 在腾讯云 EdgeOne 控制台创建/选择 Pages 项目，将构建产物或静态目录上传/关联 CI，发布后可获得公网访问地址（如 `https://xxx.edgeone.app`，以控制台为准）。
3. **无需**为「Dify 自动部署」单独申请 EdgeOne API Token；若团队不使用插件流水线，可不配置该 Token。

步骤3：联调与验收
1. 在已发布站点上测试：① 简历文件+JD 文件；② 简历文字+JD 文字。
2. 检查：优化文本可读、HTML 在预览区内样式正常、关键词高亮、无控制台跨域错误；后端日志无密钥泄露。
3. HTML 展示异常时优先排查：模型输出的 HTML 是否完整、是否引入外链资源；前端是否采用推荐的 iframe sandbox 策略。
四、关键注意事项（必看，避免联调与上线异常）
1. HTML 生成规范：AI 输出的 HTML 须完整（核心标签齐全）、无语法错误、**不依赖外部图片/外链样式脚本**，否则前端嵌入预览易失败或带来安全风险；后端宜做 HTML 消毒（allowlist），前端配合 sandboxed iframe。
2. 文件上传限制：Dify 侧通常仅支持 Word/PDF 等限定格式，需在页面与文档中告知用户，或引导改用文本粘贴。
3. 密钥与调用：**Dify API Key 仅在后端（或受控边缘函数）环境变量中配置**；静态资源中不得硬编码密钥；详见 [frontend-architecture.md](./frontend-architecture.md)。
4. 测试覆盖：Dify 控制台内测两种输入方式；上线后再测公网站点全流程（含大文件、超时、错误提示）。
5. EdgeOne Pages：主要负责静态资源分发；**调用工作流的是你的后端**，不是 Pages 本身「内置调用 Dify」。
6. 报错处理：预览异常时优先查 HTML 片段完整性、外链依赖、前端预览方式；接口失败时查后端日志、Dify 额度与限流。
五、后续维护（长期可用）
- **Dify API Key**：定期轮换，更新后端环境变量并重新部署后端；泄露后立即作废并重签。
- **提示词与工作流**：优化效果或 HTML 不稳定时，在 Dify 内微调节点提示词或结构，发布后继续由后端按原 API 调用即可。
- **前端与静态发布**：静态资源更新后按 EdgeOne Pages 流程重新发布；若 JSON 字段变更，需同步改后端与前端解析逻辑。
- **功能扩展**：可在工作流中增加导出、多版本对比等能力，后端聚合输出字段后，前端再扩展展示即可。
